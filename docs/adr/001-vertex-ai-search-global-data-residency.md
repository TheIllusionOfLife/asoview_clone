# 001. Vertex AI Search global data-residency

- **Status**: Accepted (2026-04-18)
- **Deciders**: repo owner (study clone, not production)

## Context

The `asoview_clone` dev environment runs in `asia-northeast1` (Tokyo). The rest of the data plane (Spanner, Cloud SQL, Redis, GCS, Artifact Registry, KMS) stays inside that region by design, mirroring Asoview's production topology.

Product search was originally OpenSearch on GKE in the same region. PR #62 replaced it with Google Cloud Vertex AI Search (Discovery Engine API). Discovery Engine does not currently offer an `asia-northeast1` regional endpoint for structured `SEARCH_TIER_STANDARD` data stores; the available locations are the `global`, `us`, and `eu` multi-regions. `global` was chosen to avoid pinning the index to a US- or EU-specific multi-region when no Tokyo option exists.

The product catalog indexed into Discovery Engine is:

| Field | Type | Notes |
|---|---|---|
| `productId` | string | Synthetic ID generated by commerce-core |
| `name`, `description` | string | Public marketing copy; no user data |
| `minPrice` | number | Derived from public variant pricing |
| `imageUrl` | string | CDN URL to a public product image |
| `areaId`, `categoryId`, `status` | string | Public catalog metadata |
| `popularityScore` | number | Aggregated order count, no per-user attribution |

No PII, payment credentials, authentication tokens, or user-generated content touches this index.

## Decision

Use the Discovery Engine `global` location for the product search data store (`asoview-products`) and engine (`asoview-products-engine`).

## Consequences

**Easier**
- Zero self-hosted search infrastructure: no StatefulSet, KMS key, snapshot bucket, or PodDisruptionBudget to maintain.
- Managed Japanese morphological analyzer replaces the custom `opensearch-kuromoji` image.
- Study-clone query volume is small enough that the per-query cost on the `SEARCH_TIER_STANDARD` engine is negligible. A Cloud Billing budget (see `infra/terraform/environments/dev/monitoring.tf`) caps monthly spend at $30 as a safety guardrail rather than a usage target.

**Harder**
- Product catalog data leaves `asia-northeast1`. This is acceptable because the data is public, non-PII marketing content.
- Cloud Support and latency troubleshooting spans a Google-owned multi-region, not a single GCP region we control.

**Follow-ups**
- If Google ships a regional (Tokyo) Discovery Engine endpoint, migrate the data store.
- If this clone is ever repurposed beyond the study scope (e.g. real user data, private catalogs, rights-restricted content), revisit this ADR before indexing anything beyond public catalog metadata.
- Cost guardrail: a Cloud Billing budget alert targeting the Discovery Engine service is added alongside this ADR to catch runaway usage.

## Alternatives considered

1. **Rebuild the custom OpenSearch kuromoji image**: rejected — the operational burden of a search cluster (KMS-encrypted disks, snapshot bucket, 3-replica StatefulSet, PDB, NetworkPolicy, kuromoji plugin packaging) was a large fraction of the Kubernetes surface area for a single domain concern. PR #62's goal was to eliminate that burden.
2. **Host the index in a different GCP region that does support Discovery Engine regional (e.g. `us-central1`)**: rejected — data still leaves Japan, so the residency question is not meaningfully improved, and adds another region to the topology.
3. **Wait for Tokyo endpoint availability**: rejected — no announced ETA, and the alternative (keep OpenSearch broken) is worse.
